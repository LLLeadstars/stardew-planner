# V1 决策子任务发布草稿

状态：六个子任务已发布，原生 sub-issues 关系与五条阻塞关系已核验。本文件保留为建图时的草稿快照，后续以 [GitHub 决策地图](https://github.com/LLLeadstars/stardew-planner/issues/1) 及其子任务为准。发布身份与关系记录见同目录 github-map.json。
建图只创建问题；用户尚未确认的问题不得由代理自行作答。

## 确定原版数据基线与活动耗时估算的证据

类型：research（AFK）。前置：无。

### Question

针对浇水、收获、购物、工具升级及游戏内时间，能找到哪些可靠的游戏规则、可维护的数据来源与可复用条件？推荐锁定哪个明确的原版版本，依据是什么？
区分操作本身、移动、等待、暂停和随机结果，判断哪些耗时适合按工作量估算、哪些只能由玩家预留；记录变量、不确定性与不可支持的精度承诺。
输出有来源、日期、版本范围及置信边界的研究材料，作为用户选择功能范围和估算规则的依据，不自行确认产品取舍。

## 确定首批活动清单、输入参数与提醒边界

类型：grilling（HITL）。前置：确定原版数据基线与活动耗时估算的证据。

### Question

首批每种内置活动具体支持什么、采用哪种时间输入方式、需填写哪些最少参数、展示哪些参考信息、能给出哪些有依据的提醒？
缺失条件、未知规则和玩家覆盖时长时如何处理？需要哪些初始玩家状态，如何避免先填写长档案才能开始？
以逐活动的支持矩阵、明确的排除范围及具体场景形成可实施边界。

## 确定游戏日与时间衔接的完整语义

类型：grilling（HITL）。前置：无。

### Question

游戏日的起止、时间粒度、日程起点和跨午夜如何表达？插入、删除、重排、更改时长时，顺序衔接活动如何重新计算？
固定活动冲突已确定保留时刻并提醒，但其后普通活动从哪个结束时刻继续？多重重叠、空闲、超出游戏日及手动赶路如何显示与计算？
以具体输入与预期时间表明确规则，用户确认前不得将未定语义写成实现假设。

## 确定长期目标、完成状态与每日记录的边界

类型：grilling（HITL）。前置：无。

### Question

目标、目标步骤和日程活动是什么关系，是否允许一个活动服务多个目标？活动勾选完成是否影响目标进度，完成与实际成果如何区分？
玩家切换日期、重复使用昨日安排或修改玩家状态时，日程和目标记录如何保存？在不引入完整跨天规划界面的前提下，V1 必须支持哪些日常连续使用能力？

## 验证电脑端规划主流程与编辑交互

类型：prototype（HITL）。前置：确定首批活动清单、输入参数与提醒边界；确定游戏日与时间衔接的完整语义；确定长期目标、完成状态与每日记录的边界。

### Question

玩家如何从首次进入到排好一天，完成选活动、填参数、查看估算、排序、固定时间、处理冲突和关联目标？
通过可丢弃的电脑端原型验证信息布局与编辑方式，同时覆盖首次使用、空状态、冲突和恢复已保存数据。记录用户实际反馈，区分已接受与待验证的交互。

## 确定本地保存、备份恢复与技术架构

类型：grilling（HITL）。前置：验证电脑端规划主流程与编辑交互。

### Question

在已明确的流程与模型上，选择前端技术、模块边界和本地持久化方案；明确活动规则数据如何随版本更新。
导出文件包含哪些数据、导入是替换还是合并、损坏或不兼容文件如何处理、升级迁移和保存失败如何提示？是否要求离线可用，以及浏览器支持范围是什么？
给出接口、数据结构、版本策略、错误处理与测试边界；为后续方向保留有依据的扩展空间，不预建账号、云端或分享服务。

## 发布与执行顺序

1. 恢复 GitHub 身份认证后，检查是否存在同名地图，避免重复创建。
2. 创建地图及以上子任务，并附上所需 wayfinder 类型标签。
3. 全部子任务取得身份后，再关联 sub-issues 与原生阻塞关系。
4. 核验关系，发布可读标题链接；为研究子任务分派 research 子代理，按技能要求使用独立研究分支保存材料。
5. 建图阶段结束。后续每个决策工作阶段认领一个就绪子任务，与用户解决并记录结论，再扩展地图。
6. 最终规格编写与验收的具体子任务在前置问题收敛后创建；不得现在将它标为可实施或完成。
